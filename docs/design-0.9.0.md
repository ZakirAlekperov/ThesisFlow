# ThesisFlow 0.9.0 — эксплуатационная готовность и качество интерфейса
# ThesisFlow 0.9.0 — Operational Readiness and UX Hardening

**Статус: DESIGN.** Код не изменён; это подготовка к стабильной 1.0.
Входит после завершения обязательных инкрементов 0.4–0.8.

## 1. Продуктовая цель

Превратить функциональное локальное приложение преподавателя в продукт,
который легко установить, обновить, диагностировать и использовать ежедневно,
без знаний Go, SQLite и командной строки.

0.9 не вводит новую предметную область. Работа направлена на единый UX,
безопасность локального HTTP-приложения, проверку сценариев установки,
регрессии и качество документации.

## 2. P0 — согласованность интерфейса

1. Единый layout для всех страниц: меню, хлебные крошки, заголовок,
   область сообщений, тема, состояния загрузки/ошибок.
2. Перенести копии HTML и конфликтующие inline CSS в переиспользуемые
   Go-шаблоны и стили варианта C. Без React, npm и JS-framework.
3. Унифицировать кнопки, поля, таблицы, модальные подтверждения,
   состояния пустых списков, просрочки и цвета статусов.
4. Не использовать только цвет для обозначения статуса:
   всегда понятная текстовая подпись и контраст на обеих темах.
5. Проверить клавиатурную навигацию и фокус; активные вкладки,
   формы, таблицы и детали доступны без мыши.
6. Исправить длинные кириллические имена, масштаб браузера 200%,
   узкие окна, горизонтальную прокрутку таблиц без потери заголовков.
7. Ввести единообразные, не раскрывающие стек/SQL, сообщения об ошибках.
   Пользователь должен знать, что сохранено, а что не сохранено.
8. Разделить предупреждения, успешные результаты и блокирующие ошибки.
   Успех показывать только после подтверждённой транзакции/публикации файла.
9. Подтверждение опасных действий (архив, восстановление, изменение профиля,
   закрытие комплекта), без дублирования одного и того же диалога.
10. Отсутствие внешних шрифтов, CDN и запросов к облаку: весь UI работает
    без интернета. Не вводить телеметрию.

## 3. P0 — установка, первоначальный запуск и обновление

11. Простой офлайн-дистрибутив для Windows x64, macOS Apple Silicon/Intel,
    Linux x64. Формат установки выбирать по проверенным потребностям
    целевых ОС; portable executable допустим там, где это проще.
12. Показывать номер бинарной версии, версию схемы SQLite, путь и свободное
    место рабочего пространства в разделе «О программе».
13. Мастер первого запуска: приветствие, проверка доступности рабочего
    каталога, исходный каталог файлов, предупреждение о резервных копиях.
    Не блокировать запуск сложными настройками, если стандартный путь подходит.
14. Если SQLite уже содержит данные, первый запуск не импортирует их
    повторно и не создаёт новую «демонстрационную группу» автоматически.
15. Демоданные — только добровольный отдельный сценарий в безопасном
    пространстве, не смешанный с реальными ВКР.
16. До миграций и обновлений проверять достаточность свободного места,
    совместимость схемы и возможность вернуть состояние из копии.
17. Повреждённые/устаревшие данные приводят к понятному сообщению
    и безопасному отказу, а не к созданию пустой базы поверх старой.
18. Обновление приложения не должно автоматически удалять рабочее
    пространство, старые ZIP-пакеты и документы.
19. Не обещать автоматическое обновление через сеть: релизы офлайн,
    проверка контрольных сумм загружаемого установщика вручную.
20. Подпись и нотариализация установщика — отдельная задача при наличии
    сертификатов и возможности CI; не считать unsigned сборку подписанной.

## 4. P0 — защита локального приложения

21. Проверить, что HTTP-сервер слушает только loopback, корректно
    закрывается и не открывает небезопасные интерфейсы сети.
22. Проверить защиту от CSRF во всех изменяющих маршрутах, включая импорт,
    архив, подтверждение, восстановление, массовые операции и комплект.
23. Проверить Host/Origin, предотвращение DNS rebinding и несанкционированного
    доступа другого сайта к локальному сервису. Loopback сам по себе
    **не означает** защиту от всех атак из браузера.
24. Подобрать безопасные заголовки: Content-Security-Policy, X-Content-Type-
    Options, Referrer-Policy, Cache-Control для пользовательских данных.
    Политика должна соответствовать реальным Go-шаблонам и inline-стилям
    до их переноса; не внедрять несовместимую CSP без проверки.
25. Выдача PDF/TXT/DOCX/XLSX: безопасные MIME, Content-Disposition,
    защита от произвольных путей, HTML-инъекций и неподдерживаемых форматов.
26. Проверить Zip Slip, symlink, нечувствительные к регистру имена,
    ZIP-бомбы и лимиты на всех путях импорта/экспорта.
27. Сообщения логов и ошибок не содержат текст ВКР, полные персональные
    данные и секреты без обоснованной диагностической необходимости.
28. Базы/каталоги доступны с минимально необходимыми правами,
    резервные ZIP явно помечаются как нешифрованные.
29. Не внедрять авторизацию с пользователями, ролями, SSO, Active Directory:
    это отдельный этап, не обязательный для локального приложения одного
    преподавателя.
30. Пройти независимый от реализации набор регрессионных тестов на
    злоупотребление маршрутизатором и подмену идентификаторов.

## 5. P1 — понятность и сопровождение

31. Пользовательская инструкция «Начало работы» на русском: установка,
    добавление группы, импорт XLSX, профили требований, загрузка и
    рецензирование, комплект, резервная копия и восстановление.
32. Справка по полям, статусам и ошибкам встроена в приложение.
    Краткая контекстная справка лучше отдельного 100-страничного руководства.
33. Документация API/архитектуры, тестирования, миграций и эксплуатации
    на русском и английском; в README только актуальные факты.
34. Экран диагностики из 0.6 содержит объяснение серьёзности проблем
    и безопасные действия, а не просто «ошибка 500».
35. Журналирование с ограничением объёма, понятной диагностикой и
    возможностью экспортировать отчёт **без персональных данных**.
36. Для массовых операций — понятные результаты: сколько выполнено,
    сколько не удалось и какие действия предпринять далее.
37. Провести UX-прогон на реальных сценариях от начала до окончания ВКР,
    убрать лишние переходы и поля. Не устраивать редизайн ради эстетики.

## 6. Технический подход

- Сначала инвентаризовать существующие шаблоны и маршруты; привести к
  1–2 общим компонуемым layout, не разрабатывать собственный сложный
  template framework.
- Использовать html/template и локальные CSS/JS. Минимальные
  семантические HTML-атрибуты, доступные кнопки и формы.
- Централизовать HTTP-защиту как небольшие middleware, но не строить
  универсальную «enterprise permission system».
- Подключать миграции и проверку целостности из 0.6; 0.9 не дублирует
  внутренний журнал файловых операций.
- Не переписывать работающие SQL-репозитории, если узкая проверяемая правка
  решает задачу надёжнее.
- Критичные публичные функции документировать на русском и английском.

## 7. Измеримые критерии приёмки

1. Чистый Windows/macOS/Linux пользователь выполняет установку и импорт
   реального Excel без Go/Node/Docker.
2. Пользователь видит реальный путь данных и умеет сделать проверенный ZIP.
3. Для каждого из всех основных HTML-маршрутов проверены светлая/тёмная
   тема, клавиатура, масштаб 200%, длинные имена.
4. Нет технических ошибок без понятного объяснения действий пользователю
   в основных сценариях.
5. CSP/Origin/Host/CSRF проверяются негативными HTTP-тестами, а не
   только ревью текста.
6. Проверки с неизвестными ID, пустыми файлами, oversized multipart,
   повреждёнными ZIP, странными именами и конкурентными POST.
7. Полный прогон файлов 10 обязательных документов через UI на каждой
   ОС, включая рецензирование и выпуск комплекта 0.8.
8. Все существующие БД поддерживаемых версий обновляются без потери
   версий/замечаний; будущие схемы отвергаются безопасно.
9. Повторный запуск после отключения во время записи анализируется
   средствами диагностики 0.6 без скрытой потери документов.
10. Go: go test ./..., go test -race ./..., go vet ./..., gofmt -l .;
    проверенные сборки Windows/macOS/Linux и проверка экспортов.
11. Любое отключённое/неподдерживаемое действие ясно отмечено; UI не
    содержит фиктивных, неработающих кнопок.

## 8. План инкрементов

- dev.1: общий HTML layout и дизайн-система.
- dev.2: мастер первого запуска/настройки.
- dev.3: HTTP-безопасность и регрессионные тесты.
- dev.4: офлайн-упаковка и совместимость обновлений.
- dev.5: встроенная справка/UX/логирование.
- rc1: кроссплатформенные тесты, доступность, регрессии, документы.

## English summary

0.9.0 is an operational quality milestone: cohesive accessible UI,
safe local HTTP boundaries, straightforward offline distribution,
tested migrations, reliable error handling and usable diagnostics.
It intentionally avoids large new business modules and cloud features.
