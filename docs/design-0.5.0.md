# ThesisFlow 0.5.0 — аналитика, отчётность и контроль сроков

**Статус: DESIGN / проект на согласование.** Реализация ещё не начата.
Единая накопительная ветка: feature/0.5.0-analytics-reporting.
Один интеграционный PR в main. Никаких автоматических слияний.

## 1. Контекст / Current baseline

Интеграционный PR #58 по 0.4.0-dev объединён с main, однако P1/P2-функции
из docs/release-0.4.0.md остаются отдельно запланированными: очередь проверки,
предпросмотр, экспорт замечаний и исследование структуры DOCX.

Уже имеются: SQLite material_status/material_events, file_versions,
review_feedback, матрица статусов, готовность группы, фильтр просрочек,
панель преподавателя, печатный HTML-отчёт и импорт XLSX. Не дублировать.

### Цель

За считанные действия преподаватель определяет отстающих студентов,
документы на проверке и динамику сдачи, после чего получает воспроизводимую
выгрузку текущей ведомости.

## 2. P0 — ядро релиза

1. **Единые определения метрик.** Именованные функции: активные студенты,
   ожидаемые документы, принято, на проверке, на доработке, не сдано,
   просрочено, процент готовности.
2. **Точный знаменатель готовности.** Все применимые требования:
   групповые плюс индивидуальные, с учётом активных студентов.
   Ноль требований показывать как «нет данных», не как 100%.
3. **Архивы.** Архивные группы/студенты не участвуют в текущих показателях по
   умолчанию. В отчётах явно обозначать отбор и возможность включения архива.
4. **Отдельная семантика принятой копии.** Текущий статус «На проверке»
   не эквивалентен отсутствию старой принятой копии: показывать отдельно
   статус процесса и наличие действующей принятой версии.
5. **Групповой отчёт.** Список студентов и их обязательных документов,
   текущие статусы, сроки, доля готовности, индикатор внимания.
6. **Отчёт по всем активным группам.** Сравнение групп и сортировка
   по готовности, просрочкам, количеству материалов на проверке.
7. **Фильтры.** Группа, статус, наличие просрочек и поиск по ФИО/учебному ID.
8. **Сортировка.** По ФИО, сроку ближайшего незакрытого требования,
   готовности и числу просроченных документов.
9. **Drill-down.** Любое проблемное значение ведёт к конкретной карточке ВКР
   и соответствующему требованию без повторного ручного поиска.
10. **Сводка по просрочкам.** Показывать студента, требование, срок и количество
    календарных дней просрочки (для непринятого текущего состояния).
11. **Read-only analytics.** Отчёт строится из актуальной БД и не изменяет
    статусы или документы.
12. **Пакетные SQL-запросы.** Устранить N+1 в существующей матрице статусов;
    читать статусы одним набором/батчем, а отсутствующие считать missing.
13. **Единый дизайн C.** Доступные светлая/тёмная темы, компактная таблица,
    закреплённые заголовки там, где оправданно, ясные подписи и empty states.

## 3. P1 — отчёты и наблюдаемая динамика

14. **Настраиваемая выгрузка .xlsx.** Реальная книга Excel, не переименованный
    CSV. Таблицы «Сводка», «Студенты» и «Документы» с понятными заголовками,
    фильтрами и читаемыми датами. Никаких макросов и внешних ссылок.
15. **CSV как простой формат обмена.** UTF-8 (с учётом Excel на Windows),
    корректное экранирование полей, защита от формульной инъекции в Excel.
16. **Печатный отчёт.** Отдельный html/template с CSS для A4/A3 и понятными
    переносами; PDF через печать браузера, без обязательного PDF-движка.
17. **Период активности.** Количество загрузок (по file_versions.uploaded_at),
    решений о приёмке (по material_events accepted), возвратов (по
    review_feedback revision), с фиксированными границами периода.
18. **График событий по неделям.** Только реальные исторические события:
    поступило, принято, возвращено. Не изображать ретроспективную готовность,
    которую нельзя восстановить достоверно при изменении требований.
19. **Визуализация группы.** Горизонтальные составные полосы статусов,
    отдельный список просрочек, доступная альтернативная таблица данных.
    SVG/CSS и небольшой собственный JS по необходимости, без React/D3.
20. **Единые параметры экспорта.** На экране и в выгрузке идентичные фильтры,
    дата/время генерации и явно заданное определение всех колонок.

## 4. P2 — только после проверки практической пользы

21. Сохранённые пользовательские наборы фильтров (без отдельного
    конструктора запросов или BI-системы).
22. Аналитика задержек проверки: время между загрузкой и решением,
    **только после добавления связи решение ↔ ID версии**.
23. Исторический снимок отчёта («готовность на дату») **только после**
    проектирования снимков требований, архивов, сроков и студенческих
    назначений. Существующих событий статусов для такой функции недостаточно.
24. Экспорт уже построенных отчётов в PDF одним действием — отдельное
    решение после оценки качества браузерной печати.

## 5. Definitions / Семантика

- Required = число текущих применимых требований у включённых студентов.
- Accepted = число требований с *текущим* статусом accepted.
- UnderReview / NeedsRevision / Missing = количество требований с этими
  текущими статусами; четыре группы должны давать в сумме Required.
- Overdue = due_date < local calendar today AND current status != accepted;
  отсутствие срока не является просрочкой.
- ReadyPercent = 100 * Accepted / Required при Required > 0; иначе N/A.
- UploadedFiles = количество событий загрузки, не число студентов и не
  количество обязательных документов.
- ApprovedEvents = число событий принятия в периоде, не текущий accepted.
- Если документ ранее принят, но заменён на ещё не проверенную редакцию,
  текущий процесс не принят; старая принятая копия показывается отдельно.
- «Принято с опозданием» не считать без снимка срока, действовавшего
  на момент приёмки.
- Локальную календарную дату преподавателя применять к срокам. События
  хранить в UTC и переводить для отображения с одной зафиксированной TZ.

## 6. Proposed implementation / Архитектура

- Go 1.23+, SQLite, html/template, локальные CSS/JS варианта C.
- internal/analytics: один read-only слой выборок и расчётов, параметр
  now/time.Location для детерминированных тестов.
- internal/web: GET /reports, GET /reports/groups/{id},
  GET /reports/export.csv, GET /reports/export.xlsx,
  GET /reports/print; URL и параметры уточнить до первой реализации.
- internal/export: один типизированный ReportData -> рендереры CSV/XLSX/HTML.
  CSV использовать encoding/csv, для XLSX провести короткий технический
  выбор между узкой проверенной библиотекой и минимальным OOXML writer;
  не реализовывать большой собственный Excel-движок.
- Состояние отчёта вычислять из SQLite, не добавлять таблицы кэша процентных
  показателей. Добавлять индексы только после анализа EXPLAIN QUERY PLAN
  и реальных бенчмарков.
- Не хранить «текущую дату» в БД. Все отчёты read-only.
- Любые названия, ФИО, учебные номера, статусы экранировать html/template,
  ограничивать длину HTTP-фильтров и размер выгрузки.
- В CSV/XLSX предотвращать интерпретацию пользовательских значений как
  формул (=, +, -, @ и управляющие символы в начале).
- Стриминг там, где нужно; не строить огромный файл/таблицу целиком в памяти.
- Документировать каждую новую публичную функцию на английском и русском,
  семантические решения и ограничения — в docs.

## 7. TDD / Проверка

1. Фикстуры на настоящем SQLite и реальные DOCX/XLSX, в том числе десять
   основных документов ВКР.
2. Пустая база, группа без студентов, студент без требований, нулевой
   знаменатель готовности, групповые и индивидуальные требования.
3. Проверка четырёх статусов, первой приёмки, новой версии после принятия,
   просрочки, отсутствия даты, архива, редактирования срока.
4. Проверка согласованности результатов: карточка, матрица, отчёт, XLSX.
5. Корректное экранирование CSV, XLSX и HTML, Unicode/кириллица,
   недопустимые фильтры, обработка больших объёмов.
6. Границы периодов: календарный день, часовой пояс, переход дат.
7. Проход go test ./..., go vet ./..., go test -race ./....
8. Контроль EXPLAIN QUERY PLAN и benchmark на 100, 1000 и 5000 студентов;
   объём документов задаётся реалистично.
9. Ручное открытие экспортированного XLSX в настоящем Excel.
10. Кроссплатформенная сборка и проверка светлой/тёмной темы.

## 8. Release gates / Предусловия

**Не объявлять 0.5.0 стабильной**, пока не принят состав оставшихся задач
0.4.0 (очередь проверки, предпросмотр, комплектность, экспорт замечаний).
Возможно завершить их в 0.4.x, либо явно перевести некоторые в будущие
версии; бесконтрольный перенос без решения запрещён.

Порядок предлагаемых инкрементов:
- dev.1: однозначные метрики + SQL batch/N+1 + точные тесты;
- dev.2: UI отчётов, фильтры, drill-down;
- dev.3: CSV + XLSX, реальные образцы экспорта;
- dev.4: события по периодам, доступные графики и печать;
- rc: регрессии, производительность, TDD, cross-platform и документы.

## English overview

0.5.0 is a focused local analytics/reporting milestone for a single teacher.
It does not add user accounts, a cloud BI service, a frontend framework or
speculative historical-state reconstruction. Reports are read-only and
computed from persisted requirements, student statuses and immutable events.
Exported workbooks are real XLSX files. Release work proceeds through one
cumulative integration pull request against main; merge is owner-controlled.
