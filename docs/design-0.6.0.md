# ThesisFlow 0.6.0 — надёжность, восстановление и перенос рабочих данных

**Статус: IN DEVELOPMENT.** Первый кодовый инкремент (аудит, проверка ZIP,
CLI и диагностическая страница) реализуется в отдельной ветке;
аварийный журнал и переключение рабочего пространства ещё не завершены.
Кодовая ветка: `feature/0.6.0-reliability-implementation`.
Один накопительный PR в `main`, без автоматического слияния.

## 1. Зачем нужен релиз / Goal

К этому этапу в локальном рабочем пространстве преподавателя могут
находиться реальные документы нескольких учебных групп, принятые копии,
промежуточные версии и история рецензирования. Главный пользовательский
вопрос: «Что произойдёт с моей работой при прерванной операции, повреждении
файла, обновлении приложения или смене компьютера?».

Цель 0.6.0 — обнаруживать несогласованность и безопасно восстанавливать
работоспособное рабочее пространство **без молчаливой потери данных**.

Планы 0.4.0 P1/P2 и 0.5.0 аналитика пока не объявлены завершёнными.
Проектные PR #59 и #60 ранее не содержали работающего кода.
Кодовые PR #63 и #64 уже объединены с main; текущее приложение main перед
созданием этой ветки имело версию `0.5.0-dev`. Версию бинарного приложения не менять одним лишь
документом. Код следующей версии начинать по отдельному решению.

## 2. Проверенная исходная архитектура / Observed baseline

- `internal/storage/sqlite/sqlite.go`: один пул SQLite, включены foreign keys.
- `internal/storage/migrate/migrate.go`: `PRAGMA user_version = 1`,
  первоначальная миграция; некоторые таблицы создаются отдельными Init().
- `internal/fileversions`: неизменяемые версии + размер/хеш;
  человекочитаемые принятые копии проецирует `internal/review`.
- `internal/integrity/audit.go`: проверка хеша и размера версии, но не полный
  двунаправленный аудит принятой проекции и SQL-связей.
- `internal/backup/backup.go`: SQLite snapshot через `VACUUM INTO`, ZIP
  с manifest.json и хешами, проверка ZIP при распаковке в новый каталог.
- `cmd/thesisflow/backup_restore.go`: восстановление в отдельную папку;
  замены активной БД нет, ручной путь к переключению не оформлен.
- `internal/web/backup_settings.go`: предупреждение, что копия не зашифрована.
- `internal/web/batch_upload.go`: предварительная проверка партии,
  но поздний сбой может оставить часть документов сохранённой.
- `cmd/thesisflow/main.go`: сервер только на `127.0.0.1`, без облака/Docker.

**Критические замечания:**
1. ZIP manifest проверяет байты, но ещё не доказывает семантическую
   согласованность SQLite, ссылок на версии и принятых файлов.
2. `VACUUM INTO` создаёт корректный снимок SQLite; согласованность этого
   снимка со всеми файлами зависит от строгой блокировки операций записи и
   проверки результата, а не от одного только SQLite snapshot.
3. В ZIP существуют пределы размера архива, отдельных элементов и числа
   файлов. Они могут оказаться недостаточны для нескольких выпусков ВКР.
4. `filepath.Join` формирует системные разделители, поэтому пути, записанные
   в SQLite под Windows, требуют отдельной проверки переносимости на Linux
   и macOS. Нельзя полагаться, что перенос ZIP сам исправит ссылки.
5. Между `Lstat` и `Open` есть TOCTOU-окно. Не обещать полной защиты от
   злонамеренного процесса того же локального пользователя.
6. Старые операции через Go API могут не проходить общий HTTP-gate резервной
   копии; необходимо явно определить единого владельца операций записи.

## 3. P0 — корректность данных и аварийное восстановление

1. Зафиксировать инварианты файлового хранилища:
   `version_id` → существующий файл → размер+SHA-256; каждая принятая
   проекция соответствует `accepted_files` и валидной версии; неизвестные
   файлы никогда не удаляются автоматически.
2. Сформировать единый read-only аудит `workspace.Check`, объединяющий
   `PRAGMA quick_check/integrity_check`, `foreign_key_check`, контроль
   версий, принятой проекции и безопасных относительных путей.
3. Возвращать структурированный отчёт с категориями: отсутствие,
   повреждение, чужой/опасный путь, дублирование, несогласованный статус,
   неучтённый файл, ошибка SQLite.
4. Разделить «проверить» и «исправить»: аудит ничего не изменяет.
5. Ввести **журнал критических файловых операций** с уникальным ID,
   детерминированными шагами и подтверждением завершения. Минимальный
   охват: принятие/замена принятой версии.
6. После аварийного завершения на старте проверять незакрытые операции
   и предоставлять безопасный отчёт о том, что можно восстановить.
7. Разработать повторяемую (idempotent) процедуру восстановления
   с сохранением старых принятых байтов и без удаления неизвестных файлов.
8. Использовать атомарную публикацию временного файла там, где она
   поддерживается, с `fsync` файла и необходимой синхронизацией каталога;
   документировать ограничения Windows/сетевых ФС.
9. При невозможности однозначного восстановления маркировать
   ситуацию «Требуется внимание», а не скрывать конфликт.
10. Гарантировать, что новый upload/возврат не удаляет ранее принятую
    копию документа до подтверждённой замены.
11. Обеспечить сериализацию операций приёма/архивации/резервного снимка;
    исключить конкурирующий backup и изменение файлов.
12. Не выполнять безусловный auto-delete ни в процедуре проверки, ни при
    попытке исправления.

## 4. P0 — резервное копирование и безопасное восстановление

13. Добавить `Backup.Verify` для существующего архива без извлечения
    в активное пространство, с проверкой манифеста, хешей, SQL-целостности,
    ссылок и совместимости версии схемы.
14. Записывать формат/версию архивного манифеста и применяемую версию SQLite
    явно; сохранить чтение прежнего manifest v1.
15. Перед резервным копированием запускать preflight: свободное место,
    доступность директории, ограничения размера, отсутствие незавершённых
    операций. Не выдавать «успешно», если часть файлов была пропущена.
16. Повысить или сделать разумно настраиваемыми лимиты ZIP после
    нагрузочных тестов; читать/проверять потоково, без загрузки целых
    много-гигабайтных архивов в оперативную память.
17. Показывать результат копирования: время, размер, список проверок,
    версию схемы, предупреждение о незашифрованных персональных данных.
18. Разработать **восстановление в новое активное рабочее пространство**
    из проверенного архива, но без перезаписи открытой SQLite.
19. Последовательность: verify → распаковка staging → SQL+files check →
    явное подтверждение → закрытие БД/HTTP → переключение рабочих каталогов
    или запуск с отдельным новым workspace → повторная проверка.
20. Старое пространство сохранять неизменным до завершения проверки нового;
    при сбое активации обеспечивать возврат к нему.
21. Запретить восстановление поверх занятой директории. Не принимать
    ZIP с обходом путей, symlink, коллизиями регистров имён на Windows,
    сверхлимитной распаковкой или неподдерживаемой будущей схемой.
22. Не обещать автоматический фоновый бэкап по расписанию в 0.6.0:
    это отдельный механизм хранения нескольких копий и контроля свободного
    места; выбрать его после надёжной ручной операции.

## 5. P1 — перенос между Windows/macOS/Linux

23. Предусмотреть явный экспорт **переносимого рабочего пространства**:
    SQLite + хранилище + manifest + версия схемы/приложения, без абсолютных
    путей и секретов конфигурации текущего компьютера.
24. Канонический формат внутреннего относительного пути: `/` в БД/архиве.
    На границе ОС преобразовывать через `filepath.FromSlash`; старые пути
    нормализовать **только после** проверки и с резервной копией.
25. Сохранить Unicode/кириллицу в папках; учитывать Windows reserved names,
    коллизии нечувствительного к регистру FS и длину компонент пути.
26. На новом компьютере предложить «Создать рабочее пространство из копии»,
    с предпросмотром: группы, студенты, версии, принятые документы, размер.
27. Сформировать понятную пользовательскую инструкцию Windows→macOS,
    macOS→Windows, Windows→Linux, включая проверку после переноса.
28. Не связывать перенос со сменой формата данных или облачной синхронизацией.

## 6. P1 — диагностика и упаковка

29. Локальная страница «Состояние хранилища» в дизайне C: зелёный/жёлтый/
    красный статус — только если он реально выведен из результатов проверок,
    с доступными деталями и исправимыми действиями.
30. Команды `thesisflow doctor` и `thesisflow backup verify <file>` для
    диагностики без запуска браузера и без изменения данных.
31. Логи в пользовательском каталоге: минимальные, ротируемые, без содержимого
    документов, исходных имён и персональных данных без необходимости.
32. Проверка Windows/macOS/Linux: запуск без Docker, браузер на loopback,
    штатное завершение, каталоги конфигурации и прав доступа.
33. Защитный механизм обновления схемы: preflight миграций, тесты переходов,
    отклонение будущих версий БД и понятный сценарий downgrade.
34. Формировать артефакты сборок с идентификатором версии и SHA-256,
    контроль упаковки и manifest файлов релиза.
35. Отдельно исследовать подпись Windows/macOS и notarization. Не делать
    их блокирующим требованием без сертификатов и доступа к CI-секретам.

## 7. Scope controls / Что НЕ входит

- Multi-user roles, SSO, LDAP, Active Directory, облако, синхронизация.
- Постоянный сервер/служба и обязательные фоновые агенты.
- Собственная система шифрования ZIP/хранения паролей: для шифрованных
  архивов возможен отдельный проект на проверенной криптобиблиотеке.
- Автоматическое «лечение» неизвестных файлов, массовые удаления.
- Сложная архитектура плагинов, Docker или фронтенд-фреймворки.
- Заявления об абсолютной атомарности SQLite+FS на всех ОС/типах дисков.

## 8. Engineering architecture / Модули

- `internal/workspace`: корневые пути, инварианты, аудит, совместимость.
- `internal/operations`: один простой журнал жизненного цикла критических
  файловых операций (не универсальный транзакционный движок).
- `internal/backup`: Export + Verify + RestoreToNewWorkspace поверх
  существующего manifest v1 с версионированием формата.
- `internal/storage/migrate`: проверяемая последовательность миграций.
- `internal/web`: status/doctor, backup verify, переключение рабочего
  пространства через безопасный отдельный этап запуска.
- `cmd/thesisflow`: CLI doctor/verify/move с общими сервисами.
- Только стандартные HTML-шаблоны Go, CSS варианта C и минимальный JS.
- Опасные операции требуют явного подтверждения и недоступны через GET.

### Закрытие и активация

Переключение активного workspace нельзя безопасно выполнить простым
переименованием каталога, пока открыта SQLite. Рассмотреть отдельный
restart-helper или controlled shutdown → activate → restart; зафиксировать
платформенные гарантии и строго тестировать состояние при сбое.

### Миграции

Текущее `PRAGMA user_version = 1` управляет лишь ранними изменениями,
многие таблицы создаются идемпотентными `Init()`. Не менять уже применённые
миграции задним числом. Перед будущей схемой выбрать единый порядок
создания/миграции с тестами старых БД и принудительным rollback.

## 9. Acceptance matrix / TDD

Тестировать на настоящих файлах и временных рабочих пространствах:

1. Прервать принятие документа перед записью/после временного файла/
   после rename/перед commit/после commit/во время cleanup.
2. Для каждого прерывания: повторный запуск, отсутствие потери старой
   принятой версии, предсказуемое обнаружение незавершённой операции.
3. Проверить повреждённую версию, отсутствующую принятую копию, лишний
   неизвестный файл и подменённую ссылку в SQLite.
4. Заменить файл symlink, проверить выход за каталог и TOCTOU-граничные
   случаи, документировать остающиеся платформенные ограничения.
5. Создать резервную копию; проверить manifest, SHA-256, SQL FK/check,
   ссылки на файлы и принятые копии.
6. Подменить байт в ZIP и SQLite, сломать архив, добавить опасные пути,
   дубли, огромный payload — Restore/Verify должны отказать до публикации.
7. Прервать восстановление во всех ключевых состояниях: временная папка,
   публикация, подготовка к активации, активация, повторный запуск.
8. Проверить, что исходные данные доступны после сбоя на любом этапе.
9. Перенос SQLite+files Windows↔macOS/Linux: кириллица, длинные имена,
   разделители, относительные ссылки, совпадающие без учёта регистра имена.
10. Проверить несколько выпусков: 100, 1000, 5000 студентов и реалистичное
    количество документов/версий; замер памяти, времени и размера архивов.
11. gofmt -l ., go test ./..., go test -race ./..., go vet ./....
12. Реальные сборки Windows, macOS Intel/ARM64, Linux и ручной UX-аудит.
13. README, RU/EN архитектурная документация, тест-кейсы и release notes
    соответствуют состоянию версии.

## English summary

0.6.0 is a reliability and recoverability release, not a second analytics
milestone. It focuses on a complete workspace integrity audit, a narrowly
scoped durable operation journal, verified portable backups, safe isolated
restore/activation, cross-OS relative-path compatibility, and clear local
diagnostics. It does not claim cross-resource atomicity for all filesystems,
introduce a cloud service, or overwrite active SQLite in place.

Each development increment follows TDD and joins one cumulative pull request
into main. The owner reviews and merges; no automatic merge/release tag.
