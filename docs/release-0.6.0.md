# ThesisFlow 0.6.0-dev — надёжность файлов и проверка резервных копий

**Состояние: implementation in progress / реализация продолжается.**
Этот документ описывает **фактически внесённые изменения**, а не
признак готовности стабильного релиза.

## Что реализовано (первый кодовый инкремент)

- `internal/workspace.Check` проверяет read-only:
  `PRAGMA quick_check`, `PRAGMA foreign_key_check`, хеши и размеры
  неизменяемых файлов, связи ID принятых версий с их студентами и
  требованиями, соответствие принятой пользовательской копии SHA-256.
- Нарушения формируют структурированный отчёт с кодом причины и
  идентификаторами без текста документов, ФИО и абсолютных путей.
  Не выполняется автоматическое удаление или «починка».
- `backup.Restore` после сверки ZIP-манифеста (v1) проверяет SQLite и
  файловые связи **во временной папке**. При ошибке папка не публикуется.
  Действующее пространство никогда не перезаписывается.
- `backup.Verify` позволяет проверить резервный ZIP в изолированном
  временном каталоге без восстановления поверх пользовательских данных.
- Запрещены опасные пути ZIP, системные имена Windows `CON`, `NUL`,
  `COM1` и т. д., а также коллизии файлов с отличием только регистра.
- `thesisflow doctor`: диагностика уже существующей локальной БД и
  файлов без запуска браузера, отказ при отсутствии БД вместо
  автоматического создания пустой базы.
- `thesisflow backup verify file.zip`: отдельная CLI-проверка архива.
- `GET /settings/health`: локальная страница диагностики с
  количеством сохранных версий и принятых копий, а также проблемами.
- Уведомления не раскрывают исходные пути и персональные сведения.
- Для `user_version` выше поддерживаемого приложение отказывается
  публиковать восстановленный набор данных.
- Канонический формат относительных путей новых файлов — POSIX `/`
  внутри SQLite. `fileversions.Read`, проверка целостности и принятие
  документов безопасно читают старые Windows-пути с обратными косыми
  чертами, не переписывая пользовательские файлы. Тестируются traversal,
  UNC, drive paths, повторное принятие и импорт SQLite после переноса.
- Новых обязательных SQL-таблиц и миграций в этом инкременте нет.
- Реальные SQLite и файлы используются в тестах повреждения,
  несовпадения принятой копии, неверной ссылки, повреждённого ZIP.

## Применение

На установленной версии приложения:

```bash
thesisflow doctor
thesisflow backup verify /path/to/ThesisFlow-backup.zip
thesisflow backup restore /path/to/ThesisFlow-backup.zip /path/to/NEW-workspace
```

На Windows используйте соответствующий путь к `.exe`.
В браузере: «Настройки» → «Проверить состояние хранилища».

### Как понимать результат

«Проверка пройдена» означает, что проверяемые SQL-таблицы,
версии и принятые копии согласованы в момент запуска аудита.
Результат не доказывает отсутствие будущих повреждений файловой системы,
не является антивирусным сканированием и не гарантирует, что резервная
копия пригодна для каждого будущего выпуска без миграции схемы.

При повреждении рекомендуется **сохранить копии текущих данных**,
не удалять неизвестные файлы и изучить возможность восстановления
предыдущего проверенного архива в отдельный каталог.

## Инкремент II: журнал принятия и восстановление после прерывания

Реализован в отдельном кодовом продолжении, поскольку исходный PR #65
был объединён с `main` во время работы над этим инкрементом.

- `review.Service.Init` создаёт `approval_operations` в той же SQLite,
  что и документы. Существующий формат версии схемы пока не повышается:
  новая таблица добавляется идемпотентно.
- Перед любым переименованием принятого файла намерение записывается
  **отдельной подтверждённой SQLite-операцией** с ID версии, старой
  версией, ожидаемыми путями и случайным токеном.
- Одновременные приёмки из разных `review.Service` в одном процессе
  сериализуются. Это **не блокировка второго запущенного процесса**.
- При рестарте до открытия браузера выполняется `RecoverPending`:
  если SQL commit не прошёл, восстанавливается прежняя принятая копия;
  если commit прошёл — подтверждается новая, затем очищаются проверенные
  старые файлы. Повторный запуск этой операции идемпотентен.
- При неизвестном содержимом файла или отсутствии проверенного источника
  автоматическая «починка» запрещена; приложение не открывает HTTP и
  сообщает об ошибке. Журнал сохраняется до разрешения конфликта.
- Перед созданием ZIP выполняется preflight SQL и файлов. При незакрытом
  намерении или повреждённом файле ZIP **не считается резервной копией**,
  и создание отказывается. Пользовательские данные не стираются.
- Тесты с отказами `after_intent`, `after_old_renamed`,
  `after_publish`, `after_commit` проверяют откат/завершение через
  перезапущенный сервис. Дополнительно проверяется смена расширения
  документа, редактирование принятой копии вручную, конфликт и
  невозможность повторного принятия до восстановления.
- Синхронизация файла и родительского каталога после rename добавлена
  для macOS/Linux; на Windows fsync каталога в стандартной библиотеке
  не предоставляется, что явно оговорено в `storagepath.SyncParent`.
- Помимо программных точек отказа автоматические тесты завершают
  настоящий дочерний процесс через `os.Exit`, заново открывают SQLite
  и восстанавливают тот же документ без потери старых байтов.
- Устаревшую версию документа принять нельзя: проверяем MAX(id) до
  публикации и повторно внутри SQL-транзакции. Пользовательские конфликты
  отображаются с HTTP 409 и рекомендацией по безопасному восстановлению.
- Проверка не обещает абсолютной crash-атомарности ОС и FS:
  необходимы испытания настоящего отключения питания,
  межпроцессная блокировка и отдельная процедура активации.

## Что ещё не реализовано в 0.6.0

- Испытания с реальным отключением питания/сбоем файловой системы
  и межпроцессная блокировка второго экземпляра приложения.
- Управляемая активация восстановленного workspace после закрытия
  текущей SQLite, защита от сбоев при переключении.
- Полноценный перенос абсолютных/Windows-относительных ссылок в старых
  пользовательских данных с миграционным тестированием.
- Потоковая проверка ZIP без промежуточного извлечения в каталог и
  повышение лимитов больших хранилищ по результатам нагрузочного теста.
- Двунаправленная инвентаризация посторонних файлов, не принадлежащих
  версиям или принятой проекции, и соответствующие предупреждения.
- Тесты настоящего отключения питания на разных файловых системах.
- Ротация логов, расширенная система диагностики, подпись артефактов.

**Не объединять статус релиза 0.6.0 с готовностью одного инкремента.**
Полный список и порядок — `docs/design-0.6.0.md`.

## Приёмочные проверки

1. Загрузить документ через браузер, принять его и открыть
   `/settings/health`: обе файловые копии должны проверяться.
2. На отдельном тестовом workspace повредить принятую копию:
   диагностика отмечает нарушение и не перезаписывает файл.
3. Создать ZIP до повреждения, выполнить CLI `backup verify`.
4. Попробовать экспортировать ZIP **после** повреждения: он должен
   завершиться отказом без создания архива. Искусственно созданный ZIP
   с корректным манифестом, но неверной файловой проекцией также
   должен отвергаться при Verify/Restore.
5. Проверить, что архив с неподдерживаемой схемой также отвергается.
6. На свежей Windows и macOS проверить резервное копирование и
   восстановление в отдельный каталог; исходные файлы не меняются.
7. Выполнить `go test ./...`, `go test -race ./...`,
   `go vet ./...`, `gofmt -l .`.

## English summary

0.6.0 includes a read-only SQLite and document integrity audit, local
doctor and verified ZIP recovery, plus a durable SQLite approval-intent
journal. File publication is hash-guarded and startup recovery follows
the committed DB row; real subprocess-termination tests cover both sides
of SQL commit. Linux/macOS parent-directory fsync is included, while
Windows durability limitations remain documented. Multi-process locking,
physical power-loss trials and safe workspace activation are still
outstanding before full 0.6.0 release readiness.


## Дополнительный инкремент — отдельное рабочее пространство и блокировка

Изменения следующего кодового PR поверх main:

- При каждом штатном запуске приложение удерживает **межпроцессную
  блокировку** пользовательской папки до остановки сервера. Это
  предотвращает одновременное редактирование одной SQLite двумя
  экземплярами новой версии ThesisFlow. Блокировка ОС снимается при
  завершении процесса; файл `.thesisflow.lock` намеренно не удаляется.
- Внешняя команда `thesisflow backup export` отказывается работать,
  пока веб-приложение владеет этой папкой. Резервное копирование через
  встроенный GUI остаётся доступным внутри работающего процесса.
- Команда `thesisflow workspace inspect <directory>` проверяет
  существующий восстановленный каталог, не создаёт отсутствующую SQLite,
  сверяет SQL/файлы и сообщает результат без имён студентов.
- Команда `thesisflow workspace run <directory>` запускает браузерный
  интерфейс **из выбранной папки**, а не из папки пользователя по
  умолчанию. Это действие работает только для данного запуска.
- До запуска проверяются структура каталогов, SQL-целостность и
  поддерживаемость схемы. После разрешения аварийных операций выполняется
  полный файловый аудит до начала HTTP-обслуживания.
- Отсутствующая, повреждённая или слишком новая база, символические ссылки
  на файл БД и чужие блокировки не приводят к созданию новой пустой БД
  в месте восстановленной копии.
- **Без перезаписи и без изменения настройки** рабочего пространства по
  умолчанию. Это альтернатива опасной подмене файла SQLite при работающем
  приложении, а не полностью автоматический мастер переключения.
- Для копии на другом компьютере сначала перенесите проверенный ZIP,
  затем восстановите его в новый каталог через `backup restore`.
  Не запускайте разные версии приложения одновременно с одним каталогом.
- Блокировки кооперативные: сторонние программы, старые версии
  ThesisFlow без этой блокировки и злонамеренные процессы с правами того
  же пользователя не обязаны её соблюдать.
- Файловая блокировка не заменяет резервное копирование, журнал аварийных
  операций и тесты с физическим отключением питания.

### Типичный сценарий

```text
thesisflow backup restore copy.zip /path/to/recovered
thesisflow workspace inspect /path/to/recovered
thesisflow workspace run /path/to/recovered
```

После проверки восстановленной папки закройте её экземпляр обычным
способом. Для возврата к привычным данным запускайте ThesisFlow без
аргументов. Обе рабочие папки сохраняются.

### English

An operating-system advisory file lock now protects the complete server
lifetime and prevents a second ThesisFlow process (or external CLI export)
from accessing the same workspace concurrently. A teacher can inspect
an existing restored folder and explicitly run that **separate** workspace,
with preflight SQLite checks and a post-journal recovery file audit.
No active database is overwritten, no global preference is switched, and
no unsupported future schema is opened.


## GUI: мастер выбора восстановленной копии (дополнительный инкремент)

- **Настройки → Восстановление из ZIP** создаёт отдельную проверенную
  копию в защищённом каталоге `restores`. Ссылка с экрана результата
  ведёт к **Настройки → Выбор рабочего пространства**.
- Экран `/settings/workspaces` показывает три шага: восстановить ZIP,
  выбрать одну из перечисленных копий, завершить работу и вновь открыть
  ThesisFlow. Там же можно выбрать **основное пространство** для возврата.
- Список заполняется только каталогами вида
  `restore-<24 шестнадцатеричных символа>` внутри штатной папки
  `restores`; ввод произвольного пути, `..`, абсолютного имени или
  подмена символической ссылкой не допускается.
- При подтверждении проводится дополнительная проверка SQLite,
  поддерживаемости схемы, принадлежащих файлам контрольных сумм и
  текущей целостности. Неудачная проверка **не изменяет** предыдущий выбор.
- Решение сохраняется атомарно в отдельном небольшом файле
  `.selected-workspace` в основном каталоге приложения.
  Действующая SQLite и выбранная восстановленная папка не перезаписываются.
- На следующем обычном запуске `launch()` читает выбор,
  проверяет восстановленное пространство под межпроцессной блокировкой
  и лишь после этого показывает интерфейс. Если выбор испорчен или
  каталог недоступен, запуск **завершается ошибкой**, а не создаёт
  новую пустую базу.
- Новые резервные копии из браузера по-прежнему восстанавливаются
  в единый `<default>/restores`, независимо от того, какое рабочее
  пространство сейчас открыто.
- Изменение выбора **не перезапускает** текущий процесс. Для применения
  необходимо закрыть программу и запустить её снова. Не удаляйте
  прежнюю папку без самостоятельной проверки выбранной копии.
- Изоляция GUI обеспечивается CSRF, минимальными идентификаторами,
  `html/template`, строгими проверками путей, атомарной записью
  настройки и повторной проверкой перед запуском.
- Прямая CLI-команда `thesisflow workspace run <directory>`
  продолжает использовать явно указанный каталог только для своего
  запуска и не меняет настройку выбора в основном приложении.

### Проверка вручную

1. Создать ZIP-резервную копию через GUI, восстановить ZIP.
2. Открыть список восстановленных копий и выбрать новую.
3. Убедиться, что **до перезапуска** открыта прежняя группа и прежние
   принятые файлы; состояние не переключилось автоматически.
4. Завершить приложение, запустить заново, проверить студентов,
   документы, статусы и историю замечаний в восстановленной копии.
5. Выбрать «Основное рабочее пространство», перезапустить и
   убедиться, что исходные данные не изменились.
6. Повредить **тестовую** копию, проверить отказ выбора и отсутствие
   изменения файла `.selected-workspace`.
7. Проверить блокировку второго экземпляра приложения, восстановление
   после сбоя и `go test -race ./...`.
8. Проверить Windows/macOS/Linux и реальные ZIP с кириллицей.

### English

The recovery UI now includes a three-step workspace picker. It lists only
verified-format restore directories inside the application's private
recovery root, checks SQLite and document hashes before persisting the
next-launch choice atomically, and rechecks on application startup under
an OS lock. No active SQLite connection is replaced; switching requires
normal application restart, and users can select the original workspace
again. Corrupt selection state fails explicitly instead of creating an
empty database.
