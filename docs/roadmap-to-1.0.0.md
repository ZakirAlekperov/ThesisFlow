## 2. Объём работ и последовательность

### 0.4.0 — завершить практический цикл проверки

- Очередь документов на проверку; переход к конкретной версии.
- Контроль комплектности по группе и студенту; не дублировать будущую
  бизнес-логику финализации 0.8.
- Предпросмотр PDF/TXT безопасным локальным HTTP, DOCX — только если
  есть поддерживаемый и проверяемый способ без внешнего офиса.
- Доступная история/экспорт замечаний; полный тест с реальными файлами.
- «Автоматическая проверка ГОСТ/DOCX» — исследование, НЕ блокер релиза.

### 0.5.0 — аналитика

- Единый источник определения метрик, N+1 → пакетные чтения.
- Просрочки, отчёты, фильтры/сортировка, переходы к карточкам.
- Настоящие XLSX, CSV с защитой от формул, печатный HTML.
- Динамика **событий**, не выдуманная историческая готовность.
- Верификация результата с документной матрицей.

### 0.6.0 — надёжность

- Двунаправленный аудит SQL/хранилища/принятых файлов.
- Журнал критических операций и аварийные тесты.
- ZIP Verify с совместимостью старых архивов и проверкой связей.
- Безопасное восстановление/активация в отдельный workspace.
- Перенос между ОС и нормализация внутренних относительных путей.
- Doctor/diagnostics без удаления неизвестных данных.

### 0.7.0 — рабочие профили и календарь

- Версионируемые глобальные профили документов.
- Атомарное применение профиля к группе после preview/diff.
- Правила сроков и повторного применения; изменения живых групп
  только после подтверждения, без порчи файлов.
- Календарь и групповые сроки; персональные исключения — P1.
- Пользовательские шаблоны и экспорт профилей — P1 после 0.6.

### 0.8.0 — завершение ВКР

- Проверяемый набор актуальных принятых документов.
- Неизменяемый ZIP-комплект с manifest/SHA-256 и фиксацией ID версий.
- Новые ревизии комплекта без изменений старых пакетов.
- Закрытие/возобновление ВКР и связь с архивом группы.
- Формирование/публикация поверх journal и backup из 0.6.

### 0.9.0 — эксплуатационная готовность

- Единый HTML layout дизайна C, доступность, предсказуемые ошибки.
- Первый запуск и установка офлайн на Windows/macOS/Linux.
- Безопасность локального HTTP, CSRF/Host/Origin/MIME, тесты.
- Прогон обновлений на реальных старых БД, диагностика.
- Пользовательская помощь, поддерживаемые сборки и release runbook.

### 1.0.0 — стабильный выпуск

- Feature freeze; устранение критических ошибок.
- Проверка всего сценария от Excel до итогового ZIP и восстановления.
- Реальные файлы 10 материалов, история версий и замечаний.
- Аварийные и кроссплатформенные тесты, контроль SHA-256.
- Документация, changelog, тестирование установщиков.
- Личный review владельца и только после этого релизный тег 1.0.0.

## 3. Зависимости

- 0.4 → 0.5: метрики используют проверенные состояния документов.
- 0.4/0.5 → 0.7: профиль и сроки должны одинаково отображаться в отчётах.
- 0.6 → 0.7: пользовательские профили и шаблоны должны переживать backup.
- 0.6 + 0.7 → 0.8: финальный комплект фиксирует корректные принятые
  документы действующего профиля, журнал операций защищает публикацию.
- 0.4–0.8 → 0.9: UX и безопасность проверяются на всём готовом продукте.
- 0.9 → 1.0: выпуск только после реальных критериев приёмки.

При обнаружении риска для пользовательских файлов он исправляется
сразу в ближайшем рабочем PR, а не откладывается до номинального 0.6.

## 4. Scope gate — против избыточной функциональности

Обязательный 1.0 — локальный преподаватель, не enterprise EDMS.
Реалистичная ценность важнее числа функций. Отложить после 1.0:
- личные кабинеты/роли/SSO/LDAP/AD;
- сложные согласования, предзащиты, электронные подписи;
- онлайн-синхронизацию, удалённые сервисы и фоновые агенты;
- полную автоматическую экспертизу ГОСТ и слияние DOCX;
- архитектуру плагинов и универсальные схемы документооборота.

Принцип: P0 обязателен; P1 принимается после подтверждения пользы и
возможности полноценно протестировать; P2 — исследование/будущие версии,
не препятствует 1.0 без отдельного решения.

## 5. Организация GitHub и TDD

- Данный **единый planning PR** содержит спецификации 0.8, 0.9, 1.0
  и дорожную карту целиком. Он не вводит бинарную версию и не считается
  выпущенным функционалом.
- Когда начнётся программирование, создать **ровно один интеграционный
  PR в main на каждую фактически реализуемую версию**.
- Внутри PR — небольшие коммиты TDD: failing test → минимальный код →
  улучшение → документация RU/EN → review → проверка. Не создавать
  десятки требующих ручного слияния feature PR.
- Публично фиксировать чек-лист функций: planned / implemented /
  tests passed / manual QA passed. Не смешивать эти состояния.
- Ни один PR автоматически не сливать. Владелец принимает PR сам.
- Реальные файлы DOCX/XLSX обязательны для интеграционных сценариев.
- Сверять README и версию бинарника с реально реализованным объёмом,
  не обещать функции по одному лишь roadmap.
- Начинать код со **завершения 0.4.0**, а не с 0.8/1.0.

## 6. Решения, необходимые перед началом кода

1. Утвердить P0 каждого релиза и обязательность P1.
2. 0.4: договориться, является ли встроенный preview DOCX обязательным;
   предпочтение — PDF/TXT, DOCX без конвертации допускается скачивать.
3. 0.6: согласовать безопасную активацию восстановленного рабочего пространства
   только при закрытой БД, с откатом и без неявного удаления.
4. 0.7: профиль — шаблон, не живая ссылка на группы; индивидуальные
   переопределения сроков как отдельные значения.
5. 0.8: архивировать проверяемые неизменяемые исходные версии, не склеивать
   DOCX. Правило завершения — все текущие обязательные требования приняты.
6. 0.9/1.0: состав поддерживаемых ОС и минимальные acceptance gates.

## English summary

The complete roadmap runs from the partly implemented 0.4.0-dev through
analytics (0.5), recoverability (0.6), reusable workflows (0.7),
immutable final thesis packages (0.8), product hardening (0.9), and
verified stable release (1.0). Planning PRs do not equal feature
implementation. One cumulative integration PR will be used per code
version, with TDD and owner-controlled merging.
