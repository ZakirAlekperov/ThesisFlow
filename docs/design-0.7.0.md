# ThesisFlow 0.7.0 — управление учебным процессом / Teacher Workflow

**Статус:** DESIGN, решение и реализация ожидаются. Этот PR содержит только спецификацию.
**База:** main (на момент проектирования бинарник `0.4.0-dev`).
**Ветка:** `feature/0.7.0-teacher-workflow`.
**PR-правило:** один накопительный pull request в main, без автоматического слияния.

## 1. Назначение версии

Сократить настройку нового набора студентов и нового выпуска ВКР. Преподаватель
создаёт один повторно используемый профиль документов, применяет его к группе,
при необходимости корректирует сроки и получает ясный локальный календарь
обязательных материалов.

Это самостоятельный этап после проектных версий 0.5 (аналитика) и 0.6
(надёжность). PR #59 и #60 были объединены с main, но оба содержали только
проектные документы: **сами функции 0.5 и 0.6 пока не реализованы**.
Поэтому это архитектурное проектирование будущей 0.7.0, не готовый релиз.
Верхние приоритеты 0.4 остаются незавершёнными, пока не реализованы явно.

## 2. Проверенные существующие возможности

- `requirements.Requirement`: ID, GroupID, StudentID, Title, DueDate.
- Общегрупповое требование хранится только один раз; все студенты группы
  видят его через `ListForStudent`, без копирования на каждого.
- `requirements.Update` редактирует название/срок, сохраняя ID;
  изменение названия запрещено, если есть принятый файл, чтобы не ломать
  человекочитаемую проекцию.
- Персональные требования уже возможны через `requirements.Create`.
- Раздел `/templates` сейчас представляет встроенный статический каталог
  тестовых DOCX/XLSX/TXT, а не пользовательскую библиотеку профилей.
- SQLite хранит события сдачи, приёмки и рецензирования; используется один
  локальный Go-сервер, `html/template`, CSS варианта C, без React.
- Резервное копирование и переносимый workspace запланированы к усилению в 0.6.

## 3. Пользовательские сценарии P0

1. Преподаватель открывает отдельную страницу «Профили требований».
2. Создаёт профиль «ВКР — 10 обязательных документов».
3. В профиле задаёт список документов: титульный лист, введение, список
   сокращений, главы 1–3, заключение, список источников, приложения 1–2.
4. Изменяет порядок обязательных материалов перетаскиванием либо доступными
   кнопками «Выше/ниже» без зависимости от JavaScript.
5. Отмечает для каждого пункта обязательность, краткое описание и
   рекомендуемый срок, если такой срок является частью профиля.
6. Получает предпросмотр профиля до сохранения, включая дубликаты и
   потенциально неоднозначные названия.
7. Выбирает группу и применяет готовый профиль через мастер.
8. До записи видит изменения: какие требования будут добавлены, какие
   совпадают, где существуют конфликты.
9. При первом применении требования получают новые *групповые* ID.
   Никаких требований-копий на каждого студента не создаётся.
10. Любой новый студент группы наследует актуальные требования группы.
11. Применение к группе с документами не заменяет файлы и не обнуляет
    историю, статусы или даты сдачи.
12. Повторное применение идентичной ревизии профиля — идемпотентно,
    не дублирует требования и не создаёт повторных событий.
13. Конфликты имён разрешаются явно; автоматическое переименование
    уже принятых документов запрещено.
14. Пользователь может оставить профиль группы индивидуально отличающимся
    от глобального образца без изменения всех остальных групп.
15. Изменение общего требования внутри группы немедленно применяется ко
    всем ВКР этой группы через существующую модель наследования.

## 4. Календарь и сроки P0/P1

16. Отдельная страница «Календарь документов» показывает требования со
    сроками: сегодня, ближайшие 7 дней, позже, просрочено, без срока.
17. Календарь должен работать без сети и фоновой службы; состояние
    пересчитывается при открытии страницы.
18. «Просрочен» = срок раньше локального календарного дня и текущий статус
    отличен от `accepted`; наличие старого принятого файла показывает
    отдельно и не подменяет текущий статус проверки.
19. Преподаватель пакетно назначает сроки выбранным *групповым требованиям*
    из одной группы с предпросмотром изменений.
20. В дальнейшем можно задавать индивидуальное исключение срока студенту,
    не изменяя общий срок группы. Для этого нужен отдельный override,
    а не копирование группового требования с тем же названием.
21. Приоритет наследования срока: персональное исключение (если есть) →
    срок группового требования → «срок не назначен».
22. В индивидуальном исключении различать «наследовать» и «срок
    намеренно не назначен», если оба поведения поддерживаются.
23. Изменение сроков не меняет дату реальной сдачи и не создаёт событие
    `material_events`, которое обозначало бы изменение статуса файла.
24. В журнале изменений сроков отдельно сохранять кто/что/когда и
    старое/новое значение; в однопользовательском режиме субъект —
    «локальный преподаватель», без фиктивных ролей.
25. Для нового учебного года возможно создавать отдельную группу с
    тем же профилем, не делая академический год новым обязательным уровнем
    сложной оргструктуры.

## 5. Профили и файлы-шаблоны P1

26. Разделить два понятия: «профиль требований» определяет список
    обязательных материалов; «шаблон файла» является скачиваемым
    DOCX/XLSX/TXT, который помогает студенту оформить конкретный документ.
27. Добавить пользовательскую библиотеку файлов-шаблонов с коротким
    описанием, назначением и привязкой к виду документа; существующий
    встроенный тестовый каталог продолжает работать.
28. Сохранять загружаемые шаблоны отдельно от студенческих версий,
    с безопасными именами, проверкой расширения/размера и хешем.
29. Назначение шаблона требованию — необязательная ссылка:
    принятие студенческого документа не зависит от наличия шаблона.
30. При замене файла-шаблона сохранять историю версий или явно предупреждать,
    что прежняя версия больше недоступна; предпочтительна неизменяемая
    версия плюс активная ссылка.
31. Шаблоны/профили участвуют в резервном копировании, проверке целостности
    и переносе рабочего пространства (требуется совместимость с задачами 0.6).
32. Отдельно предоставить «Скачать профиль»/«Импортировать профиль»
    как переносимый JSON с версией схемы и только логическими ID,
    без абсолютных путей или данных студентов.
33. Импорт профиля сначала показывает различия и не модифицирует существующий
    профиль без согласия.

## 6. Критическое решение об обновлении профиля

**Не связывать существующие группы с редактируемым глобальным профилем по
живой ссылке.** Это привело бы к неожиданному изменению требований уже
идущей ВКР и потенциальному конфликту с принятыми файлами.

Предлагаемая модель:
- Профиль — повторно используемый **версионируемый шаблон**.
- Применение фиксирует `profile_id`, `revision` и соответствие
  `profile_item_id → group_requirement_id`.
- В группе существуют обычные текущие требования с постоянными ID.
  Их редактирование распространяется на всех студентов этой группы.
- Редактирование глобального профиля создаёт новую ревизию, но
  **не обновляет действующие группы автоматически**.
- Преподаватель может выбрать «Обновить профиль группы»: сначала
  предпросмотр diff, затем явное подтверждение.
- Удаление/переименование текущего обязательного требования с принятыми
  документами не должно выполняться автоматически.
- Добавление нового пункта после обновления профиля создаёт новую колонку
  у всех студентов группы — об этом нужно предупредить заранее.
- Изменение типа обязательности и срока должно отражаться в отчётах и
  истории настроек; нельзя переписывать исходные события сдачи.

Объекты профиля хранят ссылку на исходную ревизию для воспроизводимости
применения. Формат входных данных должен поддерживать перенос профиля
без привязки к DB ID другого компьютера.

## 7. Предлагаемая модель данных

Новые сущности, только после согласования API и миграций:

- `requirement_profiles`: id, name, description, created_at, archived_at.
- `requirement_profile_revisions`: id, profile_id, revision_no, created_at.
- `requirement_profile_items`: id, revision_id, logical_key, title,
  description, position, required, recommended_due_rule (optional).
- `group_profile_applications`: id, group_id, profile_revision_id,
  applied_at, operation_id.
- `group_profile_bindings`: application_id, profile_item_key,
  requirement_id — стабильное сопоставление без догадок по названию.
- `requirement_due_overrides` (P1): student_id, requirement_id,
  due_date / override_kind, changed_at; FK и проверка принадлежности.
- `requirement_change_events`: логический объект, ID, старое/новое
  значение, время, категория изменения (не смешивать с событиями
  сдачи файла).
- `template_assets` и `template_asset_versions` (P1):
  логические метаданные, путь относительно корня, размер, SHA-256.
- Не вводить сущности `department`, `program`, `staff_roles`,
  `students_accounts`, если нет прямой потребности MVP.

Важно: наличие `required` у профиля ещё не определяет, как считать
необязательное требование в текущей модели `requirements`, где все
требования обязательны. В P0 **все применяемые пункты обязательны**;
опциональные элементы вводить только вместе с корректной семантикой
материальных статусов и аналитики.

Сроки профиля не должны зависеть от календарных дат прошлого выпуска.
P0: переносим названия и порядок, а реальные даты пользователь назначает
на уровне новой группы. Относительные сроки и правила по учебному году —
будущая функция после отдельного обсуждения.

## 8. UX — вариант C

Навигация: «Группы», «Профили требований», «Календарь», «Панель преподавателя»,
«Шаблоны», «Управление». Не делать десять независимых разделов в меню:
связанные профили и шаблоны можно объединить на одной странице с вкладками.

На странице группы: текущий профиль (и ревизия), список документов,
«Назначить профиль», «Обновить профиль», «Изменить сроки».
У каждого опасного действия — экран предпросмотра с указанием последствий.
Применение профиля возможно без JS; любые фоново обновляемые календари
и SPA-переходы исключены.

Критичные свойства: доступность для клавиатуры, роли/заголовки HTML,
светлая/тёмная тема, длинные русские названия документов, корректная
переносимость Excel/Word на Windows.

## 9. Архитектура

- `internal/profiles`: модель профиля, ревизии, проверка дубликатов,
  план изменения группы, транзакционное применение.
- `internal/requirements`: остаётся единственным владельцем активных
  требований группы; не создавать второй источник истины.
- `internal/schedule`: вычисление календарных представлений и дедлайнов;
  зависимость от Clock/Location для тестирования.
- `internal/templates` (P1): пользовательские шаблоны документов,
  проверка путей/хешей, отдельное файловое хранилище.
- `internal/web`: серверные формы/превью, bounded requests, CSRF,
  Go html/template, CSS-вариант C, минимальный JS.
- Миграции: новые версии схемы через `internal/storage/migrate`,
  не редактировать задним числом уже применённые миграции.
- Профили не должны содержать личные данные студентов.
- Никаких React/Next.js/SPA, Docker, удалённого сервера или обязательного
  фонового планировщика.

## 10. Гарантии и контроль ошибок

34. Применение профиля транзакционно: при конфликте ни один пункт не
    должен появиться частично.
35. Одновременное нажатие «Применить» и повтор HTTP-запроса безопасны
    через ограничение уникальности + идемпотентный ключ операции.
36. Учитывать группы с архивными студентами: применение к группе сохраняет
    документы архивированных ВКР, но может менять требования группы для
    активных — предупреждать, если это затрагивает исторические ведомости.
37. Не удалять принятое требование и не менять его имя из профиля при
    существующей принятой копии.
38. Импорт JSON-файла профиля: строгий парсер, проверка объёма,
    опасных значений, версии формата и дублей.
39. При разном числе пунктов в профиле новые метрики готовности могут
    пересчитаться. Предупреждение до применения обязательно.
40. Одновременно редактируемая группа: обнаружение изменения профиля
    после формирования предпросмотра и возврат 409 Conflict.
41. Резервные копии старой схемы открываются на новой сборке только после
    предусмотренной миграции; версия будущего формата отвергается.

## 11. TDD и реальные пользовательские сценарии

1. Пустой профиль, дубли названий, Unicode, максимальная длина;
   корректная сортировка.
2. Создать профиль с десятью основными документами ВКР.
3. Применить к пустой группе: десять требований, без дублирования на студентов.
4. Импортировать 20 студентов через настоящий XLSX; проверить наследование.
5. Повторить применение: количество требований не изменилось.
6. Загрузить/принять реальный DOCX; обновить мастер-профиль;
   уже принятый файл и прежние версии сохраняются.
7. Применить новую ревизию с добавленным пунктом и конфликтным названием;
   убедиться в атомарности и корректном предпросмотре.
8. Календарь: без срока, сегодня, завтра, вчера, принятый документ,
   новая версия поверх ранее принятого файла.
9. Проверить подмену ID, ложный CSRF, импорт вредоносного JSON.
10. При введении индивидуальных сроков: переопределение, возврат к
    наследованию, архивный студент и разные часовые пояса.
11. Интеграция с ZIP: профиль, связи и пользовательские шаблоны
    переживают backup/restore/перенос между ОС.
12. `go test ./...`, `go test -race ./...`, `go vet ./...`,
    `gofmt -l .`; сборки Windows/macOS/Linux.
13. Ручная проверка в браузере: светлая/тёмная темы, клавиатура,
    читаемость таблиц/форм, работа без интернета.
14. README, RU/EN инструкции и тест-кейсы обновляются по фактической
    реализации каждой функции, а не опережающими утверждениями.

## 13. Что сознательно НЕ делаем

- Личные кабинеты студентов и многоуровневое разграничение прав.
- Уведомления по email, Telegram, мессенджерам, фоновые агенты.
- Автоматическое изменение существующих рабочих групп при правке глобального
  профиля без предпросмотра и согласия.
- Полноценную образовательную оргструктуру, кафедры, направления, расписания,
  сложные согласования, предзащиту и электронный документооборот.
- Сверхуниверсальный конструктор workflow и собственную систему контроля
  документов, дублирующую действующие статусы.

## English summary

0.7.0 is a single-teacher workflow productivity milestone: reusable
revisioned requirement profiles, safe diff-based application to existing
groups, deadline planning, and optionally user-managed document templates.
Active group requirements remain the only source of truth for student
workflows; template edits do not silently rewrite existing groups. All
changes use SQLite transactions, Go server templates, existing concept C
styling and TDD. This design does not assert that 0.5.0/0.6.0 code was
shipped merely because design pull requests were merged. One cumulative PR
will hold future implementation; the owner controls merging.
