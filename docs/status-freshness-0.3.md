# ThesisFlow 0.3.0 — достоверность статусов / Status freshness

## Как проверяется задержка статуса

Источник истины: SQLite material_status. При загрузке файла операция Save
синхронно фиксирует under_review; при принятии Accept синхронно фиксирует
accepted и событие в material_events. Сервис statusmatrix.Group читает
эти состояния заново при каждом запросе GET ведомости. HTTP-обработчик
отдаёт Cache-Control: no-store.

Новый регрессионный тест воспроизводит пользовательский цикл с реальными
SQLite и файловой системой: пустая ведомость → загрузка первого DOCX →
«На проверке» → принятие первой версии → **«Принят» сразу после первого
подтверждения**, без загрузки второго документа. Чтение выполняется через
отдельный HTTP-обработчик, использующий ту же БД.

После POST интерфейс показывает подтверждение действия, основанное на
действительном завершении Save/Accept/Reject. Возврат к странице карточки
выполняется по паттерну POST–Redirect–GET. GET всегда перечитывает БД.

## Границы / Limitations

Такой тест проверяет серверный путь, но не может доказать поведение
конкретной ранее установленной сборки на компьютере преподавателя.
Если задержка повторится, потребуется зафиксировать версию бинарного файла,
URL таблицы и цепочку HTTP-запросов, чтобы исключить старый сервер/страницу
или проблему сохранения вне этой транзакции.

Также добавлена очистка временных multipart-файлов после одиночной
загрузки (ранее очистка выполнялась не во всех ветках).

EN: The test asserts that a separate handler immediately reads the accepted
status after the first real HTTP approval. Pages are non-cacheable, and a
server-side allowlisted completion notice is rendered after POST/Redirect/GET.
No polling framework or background status updater is required.
