# ThesisFlow 0.8.0 — итоговые комплекты ВКР и завершение работ
# ThesisFlow 0.8.0 — Final Thesis Packages and Closure

**Status: DESIGN.** Код не изменён. Документ относится к будущей версии.
Связанные планы: 0.4 — проверка и комплектность, 0.5 — отчёты,
0.6 — надёжность и перенос, 0.7 — профили требований и сроки.

## 1. Продуктовая цель

Помочь одному преподавателю перейти от проверки отдельных документов
к выдаче **проверяемого комплекта завершённой ВКР** и архивированию
законченного выпуска. Не пытаться заменить официальные системы согласования,
подписания и документооборота учебной организации.

Итоговый комплект должен содержать именно утверждённые редакции файлов,
явно выбранный состав, манифест и контрольные суммы. Он не должен молча
пересобираться при изменении документов в будущем.

## 2. P0 — формирование итогового комплекта

1. В карточке ВКР добавить понятное состояние готовности к формированию
   комплекта. Это **производное состояние**, а не новый статус каждого файла.
2. Учитывать групповые и индивидуальные применимые требования; не путать
   отсутствие требований с готовностью 100%.
3. Не допускать финализацию, пока есть обязательный документ без принятой
   актуальной версии, со статусом «На проверке», «На доработке» или «Не сдан».
4. Допускается отдельное пользовательское исключение требования, только
   если в модели требований уже появилась явная и проверяемая семантика
   необязательного пункта. Не превращать «нет файла» в «принято».
5. Перед созданием показать экран состава: требование, название файла,
   номер принятой версии, дата решения, размер, SHA-256, сроки и предупреждения.
6. Выделить имя и реквизиты утверждённой темы ВКР; не разрешать
   произвольно редактировать их в момент финализации, обходя правила приказов.
7. При подтверждении зафиксировать набор ссылок на ID неизменяемых принятых
   версий. **Идентичность комплекта определяется ID и хешами, не названием.**
8. Записать единый момент формирования в UTC, версию схемы комплекта,
   ID студента, ID ВКР/профиля (если существуют) и перечень документов.
9. Формировать ZIP с человекочитаемой и устойчивой структурой именования.
   Не вкладывать промежуточные версии, комментарии преподавателя или
   персональные сведения сверх необходимого без отдельной настройки.
10. Добавить манифест с SHA-256 каждого документа, размером, названием,
    ID версии и временем формирования. Архив самопроверяем.
11. Исключить абсолютные пути, управляющие символы, выход из корня ZIP,
    совпадающие имена без учёта регистра и опасные Windows-имена.
12. Не собирать ZIP из изменяемых пользовательских принятых копий:
    исходником служит неизменяемая проверенная версия в internal storage.
13. Перед публикацией проверить размер и хеш каждого источника.
    При повреждении прервать формирование, не выдавать «готово».
14. Писать архив во временный файл и публиковать после полной проверки,
    не заменяя предыдущий пакет.
15. Сохранить историю нескольких **ревизий комплекта**. Новый пакет может
    создаваться после замены документа, но старый не меняется и не удаляется.
16. Если файл или требования изменились после формирования, показывать
    «Есть изменения после формирования комплекта», а не редактировать
    ранее выпущенный комплект.
17. Предоставить скачивание комплекта и отдельную проверку его манифеста.
18. Сохранять статус «Сформирован в ThesisFlow» отдельно от официального
    утверждения/защиты. Не приписывать ему юридической силы.

## 3. P1 — управление завершением и архивом

19. Добавить явное действие «Завершить работу в ThesisFlow» только после
    проверки действующего комплекта. Завершение не удаляет материалы.
20. Не отождествлять состояние закрытия ВКР с текущим статусом отдельного
    документа и не переписывать историю приёмки.
21. Разрешить открытие закрытой карточки только через явное подтверждение;
    сохранять событие возобновления и его причину.
22. Поддержать массовую подготовку/закрытие группы через предпросмотр:
    готовые, незавершённые, конфликтующие ВКР — без частичного молчаливого
    изменения статусов.
23. Архивирование группы уже существует на уровне хранения; интерфейс
    должен объяснять разницу между «закрыта ВКР» и «архивирована группа».
24. Из карточки архивной ВКР сохранять доступ к принятым файлам,
    старым пакетам и истории рецензирования в режиме чтения.
25. Сводный список итоговых комплектов по группе: создан, требует
    пересборки, отсутствует, повреждён. Подробный экспорт метрик
    относится к 0.5 и не дублируется.
26. Включить состав комплектов и их файлы в проверку целостности и
    резервное копирование 0.6. Не хранить неучтённые ZIP вне manifest.
27. Удобная генерация сопроводительной ведомости по готовым работам
    в печатном HTML; сложные DOCX/официальные бланки — по отдельной задаче.
28. Разрешить импорт уже сформированного пакета **только** как новую
    проверенную сущность; не заменять принятые версии чужими ZIP автоматически.

## 4. Данные и API: минимальный вариант

Ввести сущности только после проверки существующих миграций:

- FinalPackage: package ID, student ID, created_at UTC, revision, manifest
  version, content hash, source snapshot, creator = local teacher.
- FinalPackageItem: package ID, requirement ID, version ID, logical filename,
  expected size and SHA-256; **FK** на существующую file_versions.
- CompletionEvent: student ID, package ID, kind = closed/reopened,
  occurred_at UTC, optional explanation.
- Активный пакет определяется отдельной ссылкой, не удалением старого.
- SQL-метаданные и ZIP — разные ресурсы: операции создания/публикации пакета
  должны использовать инварианты и журнал операций 0.6. Нельзя считать
  UPDATE + os.Rename единой транзакцией.
- Для предотвращения повторной обработки использовать устойчивый operation
  ID и проверяемую идемпотентность.
- Идентификаторы версии/требования в архивном манифесте локальны и должны
  рассматриваться как происхождение пакета, а не как ID в чужой базе.

Пути сервиса: internal/finalpackage (логика и проверка), internal/web
(просмотр/экспорт), повторно использовать internal/fileversions,
internal/requirements, internal/integrity и backup.

## 5. Требования к дизайну

Сохраняем вариант C: локальные CSS, html/template, без SPA и npm.
На карточке ВКР — вкладка/раздел «Итоговый комплект». Максимум два основных
действия: «Проверить состав» и «Сформировать комплект».
Опасные операции — только POST с CSRF. Не выполнять создание/закрытие
через GET. Длинные имена документов, кириллица, клавиатура, тёмная тема.

## 6. TDD и проверка реальными файлами

1. Полный набор из 10 документов (титул, введение, сокращения, главы 1–3,
   заключение, источники, приложения 1–2), загруженный через GUI.
2. Неполная ВКР не может стать завершённой, при этом старые принятые
   версии остаются доступны.
3. Документ ранее принят, но загружена новая версия: комплект не создаётся
   до решения по текущей версии.
4. Полный комплект создаёт ZIP с ровно 10 файлами и корректным manifest.
5. ZIP открывается на Windows/macOS/Linux, имена не конфликтуют, кириллица
   не теряется.
6. Проверка инъекции отказа до/после записи ZIP, записи SQL, публикации
   архива, прерывания приложения и последующего восстановления.
7. После первого комплекта новая принятая версия позволяет создать
   ревизию 2, а ревизия 1 не изменяется.
8. Подмена байта исходной версии или ZIP выявляется до скачивания/
   при проверке, результат не маскируется.
9. Групповые и индивидуальные требования, изменения профиля 0.7,
   архивированные записи и редактирование темы по приказу.
10. Повторение POST, параллельная приёмка документа и финализация,
    истечение CSRF и произвольный ID версии.
11. Проверка общей резервной копии и восстановленного набора пакетов.
12. go test ./..., go test -race ./..., go vet ./..., gofmt -l .;
    ручная проверка на трёх ОС.

## 7. Границы

Не включать склейку сложных DOCX в один редактируемый документ: стили,
нумерация, секции, связи, приложения и поля могут повредиться.
Не обещать автоматическую проверку соответствия ГОСТ, подписание,
электронную сдачу в ГИС/ЭДО и юридический статус архива.
Не добавлять личные кабинеты студентов.

## 8. План инкрементов

- dev.1: контракт финального состава и проверка комплектности.
- dev.2: SQL-модель неизменяемого пакета + API + TDD.
- dev.3: ZIP/manifest + публикация с журналом 0.6.
- dev.4: интерфейс, история ревизий и повторное формирование.
- dev.5: завершение/возобновление ВКР и архивные сценарии.
- rc1: восстановление/перенос/сбой/кроссплатформенная приёмка.

## English summary

ThesisFlow 0.8.0 creates reproducible, version-pinned, verifiable final thesis
bundles without changing individual accepted documents or pretending to
perform legal approval. The teacher explicitly previews and freezes the
current accepted document set; later changes require a new package revision.
No automatic DOCX merging, student accounts, or remote submissions.
