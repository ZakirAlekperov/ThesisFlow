# ThesisFlow 0.4.0 — проверка и рецензирование / Document Review

**Статус: 0.4.0-dev.** Проверка замечаний и новые функции очереди,
комплектности, PDF/TXT предпросмотра и печати истории внесены в общий
кодовый PR #63. Статус релиза остаётся «в разработке» до прохождения
интеграционной и ручной приёмки. Пользователь проверяет и сливает
единый интеграционный PR самостоятельно.

## Продуктовая цель

Преподаватель должен проводить весь цикл рецензирования в одной карточке ВКР:
получать файл, читать его, оставлять замечания к точной версии, возвращать
документ с конкретной причиной, проверять исправление, принимать окончательную
редакцию и получать достоверную историю решений.

Не добавлять студенческий портал, новые роли, облако, React/npm, сложный
маршрутизатор согласований или ИИ в обязательный объём 0.4.0.

## План реализации (постепенно, TDD)

### P0 — реализовано в первом инкременте

1. Отдельная таблица неизменяемых замечаний `review_feedback`.
2. Привязка каждого замечания к `student_id`, `requirement_id`, `version_id`.
3. Два вида записи: `comment` и `revision`.
4. Серверная проверка пустого текста, длины до 2000 символов и UTF-8.
5. Создание обычного комментария без смены статуса ВКР.
6. Возврат на доработку только с непустой причиной.
7. Транзакционная запись причины, статуса и события истории в SQLite.
8. Запрет повторного возврата уже обработанной и устаревшей версии.
9. Вывод комментариев и причин возврата в истории документа.
10. CSRF, проверка принадлежности, ограничение формы, HTML-экранирование.
11. Проверки возврата на доработку, роллбэка, XSS и повторной загрузки.
12. Текущая схема загрузок и старые принятые файлы остаются совместимыми.

## Архитектура

- Go, SQLite, html/template, минимальный локальный JavaScript, вариант C.
- Таблица `review_feedback` создаётся идемпотентно при `review.Service.Init`,
  после инициализации таблиц версий. Существующие записи не изменяются.
- Поля: авто-ID, студент, требование, версия, тип, текст, системная дата UTC.
- `AddComment`: только INSERT, не изменяет `material_status`.
- `RejectWithReason`: одно SQL BEGIN/COMMIT для status, event, reason.
- Перед возвратом проверяется, что версия самая новая и ожидает проверки.
- Комментарий к исторической версии разрешён, но решение по старой версии
  запрещено. Принятая пользовательская копия не удаляется.
- Исходные документы и их история неизменяемы.
- Все права доступа пока локальные, много пользователей в MVP нет.

### Важное ограничение

Существующий программный метод `review.Service.Reject` сохранён ради
обратной совместимости, но новый HTTP-интерфейс использует исключительно
`RejectWithReason`. Для следующего этапа нужно удалить/закрыть старый
безусловный путь в рамках отдельного архитектурного изменения.

Добавление таблицы пока выполняется через `review.Service.Init`, как и
таблицы состояний и версий. Перед стабильным выпуском требуется решить,
переносить ли все такие схемы в единый механизм версионных миграций.

## Приёмочное тестирование (реальные файлы, не фиктивные записи)

1. Создать группу, импортировать Excel и десять требований ВКР.
2. Через браузер загрузить файл «Глава 1.docx».
3. Оставить комментарий. Убедиться, что статус всё ещё «На проверке».
4. Отправить без причины — HTTP 400, статус не изменился.
5. Отправить с причиной — «На доработке» и запись причины в истории.
6. Загрузить исправленную версию — статус «На проверке», старая причина на месте.
7. Принять исправленную версию. Проверить файловую папку, ведомость и историю.
8. Проверить недействительный CSRF, чужую версию и устаревшую форму.
9. Проверить длинные замечания и текст с HTML-тегами (вывод экранируется).
10. Повторить на светлой/тёмной теме без нарушения контрастности.
11. Сделать резервную копию и восстановить её в отдельную папку:
    SQLite-связи с замечаниями должны сохраниться.

```bash
gofmt -l .
go test ./...
go vet ./...
go test -race ./...
```

## English summary

0.4.0 is a staged document-review milestone. The first increment adds
immutable per-version comments and mandatory written reasons for return for
revision. SQLite commits the new state, material history event and reason
atomically. Comments do not affect the workflow status. Old versions and
approved readable files are retained. Later increments target review queues,
safe previews, completeness reports and scoped DOCX structure validation.
